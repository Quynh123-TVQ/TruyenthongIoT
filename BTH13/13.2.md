# 13.2 · So sánh Polling và Observe

[Mục lục nhóm](README.md) · [PDF](../pdf/BTH13_TVQ.pdf)

## Mục tiêu

Đo lưu lượng trong 60 giây với pull 2 giây và notify 5 giây.
## Chuẩn bị

Server CoAP ở 13.1; Wireshark loopback hoặc server interface.

## Thao tác chi tiết

### 1. Chạy Polling riêng

Node server.cjs rồi python client.py poll --seconds 60. Bắt một tệp riêng, đếm số GET và response của flow. Polling chủ động hỏi mỗi 2 giây, dù giá trị chưa thay đổi.

### 2. Chạy Observe riêng

Chạy python client.py observe --seconds 60 trong capture mới. Request đầu có Observe=0; server trả và thông báo mỗi 5 giây. Client dùng Observe=1 hủy đăng ký khi kết thúc bình thường. Server lab hết hạn observer sau 65 giây.

### 3. Đọc token và MID

So các notify: token giữ để gắn với đăng ký; MID thay theo thông điệp, Observe sequence thay theo dữ liệu. Server này dùng NON notify nên không có ACK cho mỗi notify. Không đếm ACK của giao thức khác vào CoAP.

### 4. So sánh cùng thời lượng

Đếm packet và byte trong Wireshark cho đúng flow. Observe thường ít request khi dữ liệu đổi chậm; không kết luận luôn tiết kiệm nếu tốc độ notify quá cao hoặc có retransmission. Nhiệt độ trong server là dữ liệu mô phỏng.

### 5. Đổi sang ESP

LAB_MODE=2 cho polling hoặc 3 cho Observe, nạp coap_esp. Demo ESP tối giản không gửi hủy đăng ký khi ngắt nguồn; server tự hết hạn. Khi cần thử lại trong cùng phút, restart server để xóa observer cũ.

- [ ] Observe có option và token liên kết.

## Giải thích và trả lời

**Ai chủ động sau Observe?**

Server gửi notification theo đăng ký; client không cần GET định kỳ cho từng cập nhật.

**Token/MID đổi thế nào, đếm một phút ra sao?**

Token gắn với cùng đăng ký Observe; MID là định danh từng thông điệp, thường thay ở mỗi notification. Với polling 2 giây và notify 5 giây, lý thuyết xấp xỉ 30 request polling và 12 notification/phút cộng trao đổi mở/hủy. Số gói thực phải đếm đúng cửa sổ capture, gồm response/ACK/retry nếu có.
